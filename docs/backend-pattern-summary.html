01 / THE BIG PICTURE

ระบบเดียว แบ่งเป็นหลาย module

Backend เป็น modular monolith: deploy และรันเป็น process เดียว แต่แบ่งโค้ดตามความรับผิดชอบของธุรกิจ เช่น Source, Entry และ Fetch

Source

เป็นเจ้าของกฎและข้อมูลของแหล่งเนื้อหา

Entry

เป็นเจ้าของกฎและข้อมูลของรายการเนื้อหา

Fetch

ดูแลวงจร Fetch Job และประสานงานกับ Source และ Entry

ประเด็นที่ควรเล่า: เราได้ขอบเขตของ module ที่ชัดเจน โดยยังไม่ต้องเพิ่มความซับซ้อนของ network และการ deploy แบบแยก service

02 / CLEAN & HEXAGONAL

แยก business logic ออกจากรายละเอียดเทคนิค

นำหลัก Clean Architecture มาใช้ผ่านแนวคิด ports and adapters: แกนธุรกิจไม่ต้องรู้จัก Gin หรือ SQLite ส่วนขอบระบบทำหน้าที่แปลงข้อมูลเข้าและออก

HTTP adapterรับ request / ส่ง response
→
Serviceจัดลำดับ use case
→
Domainดูแลกฎธุรกิจ
+
Repository portสัญญาการเข้าถึงข้อมูล
←
SQLite adapterทำ SQL ตามสัญญา

ภาพนี้แสดงบทบาทและทิศทางการพึ่งพาหลัก ไม่ใช่ลำดับการเรียกทั้งหมด: service เรียกทั้ง domain และ repository port ส่วน SQLite adapter implement port

ส่วนรับผิดชอบตัวอย่าง
Domainรักษา invariant และอนุญาตเฉพาะ state transition ที่ถูกต้องตรวจสถานะก่อนเปลี่ยนสถานะ
Serviceโหลดข้อมูล เรียก domain แล้วสั่งบันทึก; กำหนด transaction เมื่อจำเป็นโหลด → ตรวจและเปลี่ยน → บันทึก
Repository portนิยาม operation ที่ service ต้องการ โดยไม่ผูกกับ SQLGetByID, Update, WithTx
AdaptersHTTP จัดการ transport; SQLite จัดการ SQL และแปลง storage errorDTO / route และ query / row mapping
Bootstrap / PlatformBootstrap ประกอบ dependencies; platform ให้เครื่องมือร่วมที่ไม่มีกฎเฉพาะธุรกิจเชื่อม handler กับ service; ใช้ transaction และ error helper

ทำไมต้องมี port? Service ระบุเพียงความสามารถที่ต้องใช้ ส่วน adapter จัดการวิธีทำจริง ทำให้ทดสอบและเปลี่ยนรายละเอียด storage ได้โดยลดผลกระทบต่อ business logic

03 / MODULE COLLABORATION

Module อื่นเรียกกันผ่าน contract ของเจ้าของ

Module ที่เป็นเจ้าของข้อมูลกำหนด API contract ของตัวเอง แล้ว module ผู้เรียกรับ contract นั้นเป็น dependency โดย bootstrap เป็นผู้เชื่อม implementation ให้

Fetch serviceผู้เรียกใช้งาน
→
Source / Entry APIcontract ที่เจ้าของกำหนด
→
Provider serviceทำงานตามกฎของ module
→
Provider repositoryเข้าถึงข้อมูลของตนเอง

ตัวอย่างในระบบ

Fetch ใช้ Source contract เพื่ออ่าน Source ที่พร้อม fetch และใช้ Entry contract เพื่อนำ Entry เข้า โดยแต่ละ module ยังเป็นเจ้าของวิธีอ่านหรือเขียนข้อมูลของตัวเอง

เส้นแบ่งสำคัญ

การเรียกข้าม module ทั่วไปไม่เข้าถึง repository ของอีก module โดยตรง โค้ดข้าม feature module จำกัดการ import ผ่าน api ของผู้ให้บริการ และตรวจได้ด้วย make check-arch

กรณี use case ที่ต้องเขียนหลาย module แบบ atomic มีแนวทาง orchestration แยกต่างหากในหัวข้อ transaction ด้านล่าง

04 / ERROR HANDLING

Error มีชนิดชัดเจน และแปลงที่ขอบระบบ

เราใช้ apperr เพื่อให้แต่ละชั้นสื่อสารความหมายของความผิดพลาดได้ตรงกัน โดยไม่ผูก domain กับ HTTP status

1. สร้างหรือแปลง

Domain สร้าง typed error สำหรับกฎธุรกิจ; adapter แปลง storage error ที่รู้ความหมาย เช่น ไม่พบแถว เป็น application error

2. ส่งต่อพร้อมบริบท

Service เพิ่มบริบทด้วย fmt.Errorf และ %w เพื่อเก็บ error chain ให้ตรวจชนิดเดิมได้

3. แปลงเป็น HTTP

Handler ส่ง error ผ่าน c.Error(err); middleware กลางตรวจชนิดและสร้าง response โดยซ่อนรายละเอียดภายในเมื่อเกิดเหตุไม่คาดคิด

ใน application

Kind บอกประเภท เช่น conflict; Code เป็นรหัสที่ client ใช้อ้างอิงได้อย่างคงที่ เลือกใช้ shared definition ก่อน และสร้างของ module เมื่อจำเป็นต้องแยกความหมาย

ที่ API boundary

ข้อความและรายละเอียดที่ส่งให้ client ต้องปลอดภัยต่อการเปิดเผย ใช้ New เมื่อไม่มีสาเหตุเดิม และ Wrap เมื่อต้องเก็บต้นเหตุไว้ใน error chain

05 / CONSISTENCY

เมื่อหลายการเขียนต้องสำเร็จพร้อมกัน

Service หรือ cross-module use case เป็นผู้กำหนด transaction boundary ตามความต้องการของงาน ไม่ใช่ให้ HTTP หรือ domain จัดการ transaction

  1. เริ่ม transaction ผ่าน WithinTransaction
  2. ผูก repository ที่เข้าร่วมแต่ละตัวกับ transaction เดียวกันด้วย WithTx(tx)
  3. ตรวจ business rules ผ่าน domain และทำการเขียนทั้งหมด
  4. หากคืน error จะ rollback; หากสำเร็จ helper จะ commit

กรณีพิเศษข้าม module: use case ที่ต้องประสานการเขียนแบบ atomic อยู่ใน internal/modules/{usecase}/service และพึ่ง module อื่นผ่าน api เท่านั้น โดย SQL ยังอยู่ใน adapter ของเจ้าของแต่ละ module

Domain ตรวจความถูกต้องของการเปลี่ยนแปลง ส่วน database ใช้ constraint และ conditional update ป้องกัน invariant เมื่อมีการเขียนพร้อมกัน
