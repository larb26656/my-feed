# Enforcing backend patterns in Go

Start with one import check for module boundaries and dependency direction. Keep the rules in [the backend architecture pattern](../patterns/architecture.md) and give each machine-enforced rule a diagnostic that links to its source. The repository’s [Makefile](../../Makefile) already provides a local backend test entry point. An architecture check could use that entry point or run as a dedicated check.

## Import checks

| Option | Fit for my-feed |
| --- | --- |
| A small Go check over `go list -json ./...` | Best fit for a rule that compares the importing and imported module names. Go reports package paths and direct imports, with separate fields for test imports. A check can allow a module’s own repository ports, allow another module’s `api` package, and reject other foreign module packages unless an explicit exception applies. The repository would own the policy and diagnostics. [Go command documentation](https://pkg.go.dev/cmd/go#hdr-List_packages_or_modules) |
| `depguard` in golangci-lint | Good for named imports that are forbidden in a layer, such as Gin in services or `database/sql` in domains. Rules select source file globs and allow or deny import prefixes. For rules that compare module ownership, enumerate module-specific pairs in configuration. [golangci-lint settings](https://golangci-lint.run/docs/linters/configuration/#depguard), [depguard upstream](https://github.com/OpenPeeDeeP/depguard) |
| `go-arch-lint` | Good for an explicit component graph. It maps directory globs to components and checks allowed component dependencies. Treat each module’s private layers and its API as distinct components if the graph must distinguish same-module repository imports from foreign imports. [Project README](https://github.com/fe3dback/go-arch-lint/blob/master/README.md), [configuration syntax](https://github.com/fe3dback/go-arch-lint/blob/master/docs/syntax/README.md) |
| Go `internal` directories | Go enforces visibility based on the import path above each `internal` directory. The current shared `backend/internal` directory still permits imports among sibling backend modules. A nested `internal` per module could enforce stricter visibility after restructuring callers such as bootstrap. [Go internal packages](https://pkg.go.dev/cmd/go#hdr-Internal_packages) |

The working-tree import graph confirms that Fetch’s `service` uses `entry/api` and `source/api`, and Fetch’s obtain adapters also use `source/api`. Preserve bootstrap wiring, test fixtures, platform packages, and the documented exception for a cross-module use case that binds foreign repository ports to a shared transaction. Scope the initial rules to production imports and choose test boundaries deliberately. A `go list` check follows the selected build configuration, so run any additional build tags or platform configurations that the repository supports. [Application service pattern](../patterns/application.md), [ADR 0004](../adr/0004-module-api-contracts.md), [Go package listing](https://pkg.go.dev/cmd/go#hdr-List_packages_or_modules)

## Enforcement by rule

| Pattern | Check |
| --- | --- |
| Module API boundaries and layer dependencies | Block invalid imports. Start by rejecting foreign concrete implementations and repositories in regular modules and module imports from `platform`. Verify allowed dependencies against the existing graph, including platform database, HTTP, and cursor helpers. [Architecture pattern](../patterns/architecture.md), [platform pattern](../patterns/platform.md) |
| Transaction ownership | A typed check could flag `WithinTransaction` calls from disallowed packages after ownership is settled. `bootstrap/source_deactivate.go` currently calls it. Shared transaction identity, rollback on failure, and atomic behavior are better verified through integration tests. [Application service pattern](../patterns/application.md), [existing bootstrap orchestration](../../backend/internal/bootstrap/source_deactivate.go), [backend test strategy](../testing/backend-tests.md) |
| Typed errors | A targeted analyzer could inspect `apperr.Definition` and check constant `Code` values against the naming convention. Use review to decide whether to reuse a shared definition and contract tests to protect client-facing codes. [Application error pattern](../patterns/errors.md), [Go analyzer API](https://pkg.go.dev/golang.org/x/tools/go/analysis) |
| HTTP, persistence, and domain behavior | Verify envelopes, error mapping, and cursor continuation using route tests. Use SQLite integration tests for constraints and conditional updates, and domain tests for allowed and rejected transitions. Review whether the business rule belongs in the domain and the transaction covers the required writes. [HTTP pattern](../patterns/http.md), [persistence pattern](../patterns/persistence.md), [domain pattern](../patterns/domain.md), [backend test strategy](../testing/backend-tests.md) |

For a recurring rule about a specific call or type, Go’s `go/analysis` provides syntax trees, resolved types, and source-positioned diagnostics. Its `singlechecker` supports a standalone command, and `analysistest` verifies expected diagnostics against fixtures. Use it when an import rule cannot express the violation, such as checking `apperr.Definition.Code` regardless of the local package alias. [Go analyzer API](https://pkg.go.dev/golang.org/x/tools/go/analysis), [analyzer test API](https://pkg.go.dev/golang.org/x/tools/go/analysis/analysistest)
